# Voy AE Assessment, Solution Documentation

This document explains what was built, why, and how each part of the brief is addressed. Code lives in `voy_ae_case_study/` (the dbt project); the headline visual is `docs/retention_curve.png`, generated by `viz/plot_retention_curve.py`.

---

## 1. The core problem, in one paragraph

The three source files look like a data-cleaning exercise, but the real problem is a grain mismatch: `activity.csv` is logged at **subscription billing-period** grain (one row per renewal cycle, and a customer can hold several concurrent subscriptions), while the brief is explicit that **retention must be measured at customer grain** ("how many subscriptions they have doesn't affect how active they are."). Every model in this solution exists to get from one grain to the other correctly, and then to make the result easy for a non-technical stakeholder to query.

## 2. What the data actually is 

| File | Grain | Key finding | What it means for the model |
|---|---|---|---|
| `customers.csv` | 1 row / customer (532,848 rows) | Two countries only: UK, Brazil. No nulls, no dupes. | Clean, static dimension attribute. |
| `acq_orders.csv` | 1 row / customer (508,694 rows) | Six real acquisition taxonomy values (Hair Loss dominates, ~75%), plus a single "Mental Health Group" row either noise or a test. Despite the filename, this is at customer level, not a transaction log. | Modelled as a static acquisition dimension. 24,154 customers have no row here, bucketed as `Unknown` rather than dropped, so they don't disappear from denominators. |
| `activity.csv` | 1 row / billing period (2,176,168 rows) | 1,482,002 distinct `subscription_id`s; most have multiple (2-30) rows (renewal cycles). 71% of customers hold more than one `subscription_id`. 43% of rows are exact duplicates of `(customer_id, from_date, to_date)` across different subscriptions. 13,107 rows end exactly on the extract's max date (2024‑08‑16), open/censored, not churned. | Must be collapsed to customer grain before "active" means anything. Right-censoring must be handled explicitly or the most recent period's churn is overstated. |
| Cross-file |, | 4,896 customers in `activity` are missing from `customers.csv`; 20,482 `customers.csv` rows never appear in `activity`; 24,154 have no acquisition row. | The customer base is built as a union of IDs across all three sources, with missing attributes coalesced to `Unknown`, so no customer is silently dropped from a metric denominator. |

**Assumptions made explicit:**
- "Active" = has at least one overlapping activity date range in the period being measured, at customer grain, regardless of subscription count.
- Country and acquisition taxonomy are treated as static attributes (no SCD), the source gives no history to track changes against. Flagged as a known simplification; SCD2 would be the fix if the source system captured changes.
- Same-`subscription_id` gaps of a few days are billing/processing lag, not a real cancel-and-return, so they were treated as one continuous relationship.
- The extract's max date is a data watermark, not a churn event, for anything still open at that date.

## 3. Architecture: staging → intermediate → marts

```
staging/        stg_customers, stg_acq_orders, stg_activity
intermediate/   int_customer_activity
                int_month_spine
                int_customer_monthly_activity
marts/core/     dim_customers
                fct_customer_monthly_activity
marts/retention/fct_customer_monthly_status
                mart_cohort_retention
```

**Staging** is a 1:1, mechanically cleaned copy of each source (typed, renamed, trimmed), no business logic. This isolates the blast radius of any future source-schema change to a single model.

**Intermediate** is where the grain problem actually gets solved:

- `int_customer_activity` collapses every subscription-period row for a customer, across all their concurrent/sequential `subscription_id`s, into continuous, non-overlapping customer-level active spans, using a gaps-and-islands window-function pattern. This is the model the rest of the pipeline depends on, and it's the one place all the messiness (overlapping subscriptions, duplicate date ranges, renewal noise) gets resolved once rather than being re-handled downstream.
- `int_month_spine` is a reusable calendar-month spine spanning the full observed date range, used both to explode islands into months and to guarantee every month appears later on, including months where a cohort had zero activity, which is what makes churn detectable at all (absence of a row is not the same as zero).
- `int_customer_monthly_activity` explodes each island across the months it touches, via a range join against the spine, producing customer × month rows.

**Marts** are what a stakeholder or BI tool actually queries:

- `dim_customers`, one row per customer: country, acquisition taxonomy, `cohort_month` (derived from observed first activity, not a separate signup field the source doesn't provide).
- `fct_customer_monthly_activity`, grain `customer_id × activity_month`. **This is the "ready to analyse, not a reporting table" output the brief asks for**: atomic enough to slice by any dimension, not pre-aggregated into a specific KPI.
- `fct_customer_monthly_status`, the same grain, with a `new` / `retained` / `churned` / `reactivated` state per customer per month. One column that makes churn, retention, and reactivation queries consistent everywhere, instead of every dashboard re-deriving its own churn logic.
- `mart_cohort_retention`, pre-aggregated `cohort_month × months_since_acquisition × country × acquisition_taxonomy`, with `cohort_size`, `active_customers`, `retention_rate`. This is the optional reporting table, and it's what powers the retention curve chart without a BI tool re-scanning the full fact table on every load.

**Why this separation, commercially:** staging gives every downstream model, and every future analyst, a single trusted definition of "what a raw row means." Intermediate is where a genuinely hard business rule (subscription count shouldn't affect activity) gets encoded exactly once, so no two dashboards can ever disagree about who's active. Marts are what Product, Marketing, and leadership actually query, a customer-grain fact table both teams can join their own analysis onto, removing the conflicting-definitions problem that usually plagues retention reporting.

## 4. Answering the brief's explicit requirements

**"Show retention over time"**, `mart_cohort_retention`, plotted as the retention curve (`docs/retention_curve.png`): one line per acquisition cohort, x-axis months since acquisition, y-axis % of that cohort still active.

**"Show retention from their initial cohort"**, `cohort_month` on `dim_customers` is derived from each customer's actual first observed activity month, not an assumed signup date. Every retention metric is anchored to it via `months_since_acquisition`.

**"Monitor key metrics, such as churn, retention and acquisition"**, `fct_customer_monthly_status` gives churn (`status = 'churned'`), acquisition (`status = 'new'`), and reactivation (`status = 'reactivated'`) as a single governed column; `mart_cohort_retention` gives retention rate. Definitions:
  - **Retention rate:** `active_customers_in_month_N / cohort_size`
  - **Churn rate:** `count(status = 'churned') / count(status in ('retained','churned'))` from the prior month's active base
  - **Reactivation rate:** `count(status = 'reactivated') / count(status = 'churned' in a prior month)`, called out separately from new acquisition, since win-back is a distinct commercial lever
  - **New customers:** `count(status = 'new')` per period

**"Be drillable by the dimensions listed here or that would exist in a relational database"**, `dim_customers` carries `customer_country` and `acquisition_taxonomy` as first-class join keys; the fact tables carry `activity_month`/`cohort_month`/`months_since_acquisition` as additional drill dimensions. Any BI tool joining the fact to the dimension gets free drill-down on all of these without touching model logic.

**"Identify customer activity over a given period"**, `fct_customer_monthly_activity` answers this directly: one row per customer per month they were active, queryable for any date range.

## 5. "Things to consider", answered directly

**"The output table should be something ready to analyse, but probably not a reporting table"**, `fct_customer_monthly_activity` is that table: customer × month grain, not pre-aggregated, but clean enough that a stakeholder can pivot it in a spreadsheet or BI tool without knowing anything about the underlying subscription mess. `mart_cohort_retention` is the optional pre-aggregated reporting table on top, included because a live retention-curve chart re-scanning the full fact table on every dashboard load isn't a good stakeholder experience at this row count.

**"Customers are active, how many subscriptions they have doesn't affect how 'Active' they are"**, this is the single rule the whole pipeline is built around. `int_customer_activity` merges overlapping/concurrent subscription periods per customer before anything downstream is calculated, so a customer with five concurrent products is exactly as "active" as a customer with one.

**"What sort of time granularity will this be useful for?"**, **Monthly**, chosen deliberately. Billing cycles in the data cluster around 30/90/180/270-day periods; daily grain would show a customer as "inactive" between billing dates that are really just processing gaps, and weekly grain would alias against the quarterly cycle. Monthly is the coarsest grain that avoids both problems, and it's the grain stakeholders actually ask retention questions in ("what's our March cohort's month-3 retention?"). Day-level precision isn't lost, it's preserved one layer down in `int_customer_activity`, and monthly is a reporting-grain decision applied on top, not a data-loss decision.

**"How would AI interact with the data?"**, By querying `fct_customer_monthly_activity` and `mart_cohort_retention` directly, an AI agent (or a text-to-SQL tool) gets clean, documented, customer-grain tables rather than having to reconstruct the subscription-overlap logic itself, which is exactly the kind of derivation an LLM is likely to get subtly wrong. More importantly, `fct_customer_monthly_status`'s single governed `status` column means an AI agent computing "churn rate" and a human analyst computing "churn rate" are guaranteed to get the same number, because neither is re-deriving the definition from scratch. This is the argument for going further and exposing these as dbt Semantic Layer / MetricFlow metrics (or LookML measures) rather than leaving them as ad hoc SQL patterns per dashboard: a governed metric layer is what actually prevents an AI agent from hallucinating its own version of "retention."

## 6. Company X's actual stack (dbt / BigQuery / Looker)

Built against dbt + DuckDB locally rather than BigQuery, to avoid GCP setup overhead for a take-home, the SQL is close to directly portable (DuckDB and BigQuery share most standard SQL and window-function syntax; the main changes would be `INTERVAL`/date-function spelling and materialization config). If this were running on BigQuery in production:

- `fct_customer_monthly_activity` would be **incremental**, partitioned by `activity_month` and clustered by `customer_country`/`acquisition_taxonomy`, it's append-mostly by month, so there's no need to rescan history on every run once the upstream islands/cohort logic (which does need full history) has run.
- Retention/churn/reactivation definitions would be exposed as **LookML measures** on an Explore joining `fct_customer_monthly_activity` (or `fct_customer_monthly_status`) to `dim_customers`, giving Product, Marketing, and leadership drill-down by country, taxonomy, cohort, and tenure without writing SQL. `mart_cohort_retention` would back the retention-curve Look directly, since it's already pre-aggregated to the shape the chart needs.

## 7. What each mart is for, commercially

- **`fct_customer_monthly_activity`**, the trusted, single source of truth for "was this customer active." Removes the conflicting-definitions problem where Product's activity number and Marketing's activity number disagree because each team wrote their own SQL. Anyone building a new dashboard joins onto this table instead of re-deriving activity from raw subscriptions.
- **`fct_customer_monthly_status`**, powers churn and reactivation reporting. Lets Product see where and when customers drop off, lets Marketing measure whether win-back campaigns are actually reactivating churned customers rather than just crediting new acquisition, and gives leadership an early warning signal (rising churn) before it shows up in revenue.
- **`mart_cohort_retention`**, powers the retention curve. Lets leadership see whether retention is improving cohort-over-cohort, and whether that differs by acquisition channel or geography, telling them where to invest between acquisition and retention work, and whether a specific taxonomy/country segment needs an intervention.

## 8. A concrete example of the reasoning process 

`int_customer_activity`'s window-function `ORDER BY from_date` initially wasn't fully deterministic: 43% of `activity.csv` rows are exact duplicates of `(customer_id, from_date, to_date)` across different `subscription_id`s (the same customer holding two products on an identical billing cycle), and DuckDB's window frame gave inconsistent results across ties between two separate window function calls in the same query. A singular dbt test (`assert_no_overlapping_period`) caught this immediately, 14,797 overlapping islands on the first run, not zero as expected.

The fix was upstream, not another sort key bolted on: `SELECT DISTINCT` on `(customer_id, from_date, to_date)` before the window step. This is correct both technically (it makes the sort provably unique, verified against the actual data) and semantically (duplicate date ranges across concurrent subscriptions carry no additional information once the model is working at customer grain, which is the whole point of the exercise). This is the clearest example in the build of a test catching a real logic bug rather than rubber-stamping a passing run, and of a design decision worth defending rather than just describing.

## 9. Known trade-offs, stated rather than hidden

- Test coverage is `unique`/`not_null`/`relationships` plus the one singular island-overlap test, sufficient to prove the crux model is correct, not a comprehensive suite. Source freshness and `accepted_values` on `customer_status` would be next additions.
- The visual is a static chart generated from a script reading DuckDB directly, not a live LookML dashboard, a deliberate time trade-off for a take-home; §6 describes what the LookML layer would look like.
- Churn and reactivation are modelled and tested (`fct_customer_monthly_status`) but only the retention curve is charted; churn-rate and new/reactivated visuals are the next visualisation to build on top of an already-correct fact table.
- Country and acquisition taxonomy are treated as static (no SCD2) since the source data gives no history to track against.
